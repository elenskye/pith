# 0007 · Word 文档引擎：自研 OOXML 局部编辑（Rust）

- 日期：2026-11-07；2026-11-08 用户确认，并用真实论文复测
- 状态：**已定**（用户：底层工具自己写，不用现成的 Rust 或 Python 库）
- 依据：Phase 0-C 与真实论文测试（`docs/feasibility.md`）

## 决定

1. Research Lab 改 Word 文件的底层（排版、引文写入、校验）用 **Rust 自研的 OOXML 局部编辑**，放在 Tauri 后端：
   - zip：未改部件按原压缩字节复制
   - XML：基于 quick-xml 的可编辑树，未改节点按原字节写回；只动格式节点
   - 校验：用**另一套解析器**（roxmltree）独立抽取文字与结构，每次写出前自动比对；不通过就不交付
2. **永远只处理副本**，不改写用户原文件；每次输出附中文报告（改了什么、没处理什么、校验结果）。
3. 排版输入分两层（真实论文测试后定）：
   - **规范（Spec）**：学校要求，结构化 JSON，可复用于多份文档
   - **计划（Plan）**：针对某一份文档——哪些粘贴来的样式其实是正文、哪些段落是题注、标题层级是否整体错位、哪些分节（封面）不能动
   - v0.2 由 Agent 生成两者、用户确认后应用（`decisions/0008`）
4. 受保护区域（如封面）：不清理、不映射；样式改动会波及它时，把原外观写成直接格式，并由校验器逐段核对「排版前后外观一致」。
5. 0-B 的引文写入（TypeScript 原型）在 v0.2 移植到同一个 Rust 引擎；citeproc-js 继续负责格式化文字（在前端 WebView 里跑，只把带格式的片段交给 Rust 写入）。

## 不选

| 方案 | 原因 |
| --- | --- |
| docx-rs | 读真实文档时库内部崩溃（三份测试文档全部） |
| docx-rust | 读写往返丢目录域、公式、修订、批注扩展部件和正文文字 |
| python-docx | 内容保真，但中文字体、按字符缩进、主题字体、脚注都要绕过 API 直接改 XML；不支持 .docm；App 要额外带 Python 运行时 |
| ooxmlsdk | 未评估；自研方案已满足要求 |

## 后果

- 每类新结构（页码分段、页眉内容、三线表、章节编号）都要自己写编辑逻辑和对应的校验；校验器保证「做不到就报告，不会悄悄改坏」。
- docx-rs 仍可作为**从零生成新文档**的候选（它主要是写入器），与编辑已有文档无关。
